# 路线图与完成条件

## 总目标

在不修改原厂核心运控树的前提下，让真机安全、可重复地完成官方六赛段，并让另一位工程师
能够仅凭仓库、设备和赛事资料复现构建、诊断、验收和比赛操作。

## 下一步严格顺序

1. 已完成：自动记录 Git commit、四枚 ARM64 二进制、配置、脚本、服务和实时安全状态。
2. 已生成 [组委会确认单](ORGANIZER_CONFIRMATION.md)；待裁判确认初次 START、暂停、恢复和
   重试边界，规则只明确允许语音/触摸“继续比赛”。
3. 用户指定三个 Type-C 暂参考铁蛋一接口定义；继续确认 CyberDog 2 三口逐一映射，并确定
   不依赖比赛电脑的实体停止方案。比赛架构已冻结为离线优先，场地网络存在与否都不依赖。
4. 在狗趴卧、四脚离地架或厂家认可工装上验证零速度 `SERVO_START/DATA/END`。
5. 低速测试停止 watchdog、许可撤销和通信中断；一次只改变一个变量。
6. 用多材质、多宽度、多偏置障碍完成超声动态数据集。
7. 在防坠工装上完成头部 ToF 真落差数据，先只触发停止，不授权前进。
8. 接入相机/雷达定位，替换 `/model_states`、世界坐标和足球真值。
9. 按 1→6 逐段实现；桥面和趴下恢复最后验证。
10. 完成比赛现场彩排、重启恢复、日志导出和备用方案。

## 每项改动的验收模板

每个新功能必须记录：

- Git commit 和机器狗部署哈希；
- 日期、场地、姿态、供电/充电状态和在场人员；
- 输入话题及原始数据文件位置；
- 预期行为、实际行为和失败条件；
- 是否连接真实运动话题；
- 急停方式和最终姿态；
- 对哪些既有测试产生影响；
- 回滚命令或恢复文件。

## 真机全程完成定义

只有同时满足以下条件才能写“真机比赛完成”：

- 单次正常开机后执行，不人工发送方向或速度；
- 六赛段物理目标全部成立，不以状态转换日志代替物理结果；
- 无线/有线通信短时故障不会造成失控；
- 急停、暂停和恢复流程经裁判允许且现场验证；
- 全程不充电，BMS 与运控状态持续健康；
- 所有感知均来自真机，不使用 Gazebo 真值；
- 规定时间内完成，终态稳定并停止输出；
- 保存完整日志、版本、配置和视频证据。
